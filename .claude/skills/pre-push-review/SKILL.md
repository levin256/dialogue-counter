# push 前の見直し

このブランチで変えたもの（`origin/main` との merge-base から HEAD まで）を見直す。実装中は動かすことを優先してよく、ここで初めて整える。

## 判断の基準

- `domain/` には、ドメインの言葉（数える・除外・ルール）を知っている処理だけを置く。知らない汎用の部品は、1 か所でしか使っていなくても `shared/lib` に置き、テストもそちらに書く
- 分けるのは、責任とテストの範囲をはっきりさせるため。先回りした汎用化（使わないオプションなど）はしない
- class は、状態とそれを使う計算がセットのときだけ使う
- 同じ値を複数の関数に引数で渡し回し始めたら、まとめる形を考える

基準は当てはめすぎない。いまのコードで困っていないものを、基準に合わせるためだけに動かさない。

## 手順

1. `/simplify` を流す。そのとき、引数で次を伝える
   - 見る範囲は、`origin/main` との merge-base から HEAD までの変更
   - 上の「判断の基準」（全文を渡す）
   - ファイルの分割・移動・新しいファイルを作るような、構造を変える直しは入れずに、提案として返すこと
2. 出てきた直しを、大きさで分ける
   - 小さい直し（重複・名前・1 ファイルの中で済むもの）: その場で直し、テストと lint を通してからコミットする
   - 大きい直し（構造を変えるもの）: 直さない。何を・なぜ変えたいかを短くまとめる
3. 見直した HEAD を記録する。小さい直しをコミットしたあとに行う

   ```bash
   git rev-parse HEAD > "$(git rev-parse --absolute-git-dir)/claude-simplified"
   ```

4. ユーザーに結果を伝える
   - 大きい直しの提案があれば、push の前に見せて、PR に載せるか、別の issue にするかを聞く（決めるのは人）
   - なければ、そのまま push してよい
