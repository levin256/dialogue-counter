# 置き場所の確かめ

## 判断の基準

層の分け方と依存の向きは、README の「ディレクトリと依存の向き」と、`biome.json` の overrides（`noRestrictedImports`）で決まっている。先にそれを読み、ここではその上で迷うところを決める。

- `domain/` には、ドメインの言葉（数える・除外・ルール）を知っている処理だけを置く。知らない汎用のものは、1 か所でしか使っていなくても `shared/` に置き（関数は `lib`、フックは `hooks`、画面の部品は `ui`）、テストもそちらに書く
- 分けるのは、責任とテストの範囲をはっきりさせるため。先回りした汎用化（使わないオプションなど）はしない
- class は、状態とそれを使う計算がセットのときだけ使う
- 同じ値を複数の関数に引数で渡し回し始めたら、まとめる形を考える

基準は当てはめすぎない。いまのコードで困っていないものを、基準に合わせるためだけに動かさない。

## 置き場所を確かめる問い

ファイルごとに、次を問う。

- このファイルの説明を 1 文で書けるか
- このファイルに、ドメインの言葉（数える・除外・ルール）を知っている関数と、知らない関数が混ざっていないか
- テストのファイルに、違う種類の話が混ざっていないか

1 文で書けない、知っている関数と知らない関数が混ざっている、テストに違う種類の話が混ざっている、のどれかなら、置き場所が混ざっているかもしれない。

## 使い方

### プランのとき

コードを書く前に、どのファイルに何を置くかの案を出す。ファイルごとに 1 文の説明を付け、基準と問いに照らした結果を添える。ユーザーと合意してから書く。

### 見直しのとき

書いたあとに、変えたファイルを同じ基準と問いで読む。

- 名前や重複のような、1 ファイルの中で済む小さい直しは、その場で直してよい
- ファイルの分割・移動のような、構造を変える大きい直しは、直さずに提案にとどめる。何を・なぜ変えたいかを短くまとめ、PR に載せるか、別の issue にするかは人が決める
